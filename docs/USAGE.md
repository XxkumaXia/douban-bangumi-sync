# 使用说明

这里是完整版说明：能同步什么、怎么配置、每个界面怎么用、豆瓣写入走的什么通道、怎么打包、怎么跑测试。
第一次来的话建议先看 [README](../README.md) 的「快速开始」。

> 仓库根目录就是扩展目录（`manifest.json` 在根），所以「本目录」指的是仓库根目录 ——
> 克隆下来不用挪位置，直接就能加载。

## 能同步什么，不能同步什么

| 能力 | 状态 |
| --- | --- |
| 豆瓣 → Bangumi：状态 / 评分 / 短评 / 标签 | 支持，走 Bangumi 官方 API |
| Bangumi → 豆瓣：状态 / 评分 / 短评 / 标签 | 支持，走豆瓣网页端接口（见下方风险） |
| 三类状态：想看 / 在看 / 看过 | 支持（搁置、抛弃不映射） |
| 分类：动画 / 三次元 / 图书 / 音乐 / 游戏 | 支持，默认只开动画 + 三次元 |
| 条目自动匹配 + 人工确认 + 手动指定 ID | 支持，映射表会缓存 |
| 写入豆瓣时**同时分享到豆瓣广播** | 支持，在同步面板逐条勾选（默认全部不分享） |
| 演练模式（只看请求不写入） | 支持，结果直接显示在「演练结果」页签，可复制/导出 JSON |

**做不到 / 需要注意的：**

1. **评分精度**：Bangumi 是 10 分制，豆瓣是 5 星制。豆瓣 → Bangumi 无损（5 档放大到 10 档）；Bangumi → 豆瓣必然有损，比如 9 分和 10 分都会变成 5 星，回头再同步就变成 10 分。**建议固定用一个站点做权威源**，不要来回互相覆盖。设置页有换算表和损耗档位提示。

   **三种换算模式**（设置页 → 同步内容 → 评分换算）：

   | 模式 | 规则 |
   | --- | --- |
   | 阶梯（默认） | 1★=2 分，每档 +2，即 2/4/6/8/10 |
   | 线性 | 星级 ×2（与阶梯在 1-5 星上结果相同，但反向分档不同） |
   | **自定义** | 自己填 1★~5★ 各对应多少分（1-10 整数） |

   自定义模式只定义**正向**（星 → 分），**反向由正向表自动推导**：分数不超过某一档的上界就归到那一星。例如填 `[2,4,5,7,9]`，则 5 分→3★、6 分→4★、10 分→5★。设置页会同时展示正向表和推导出的反向表，配错了会有黄字提示（缺档位、超出 1-10、分数不随星级递增等）。同步前用**演练**跑一遍，结果区会列出每条实际换算成多少分，可直接核对。
2. **豆瓣没有公开 API**：读取靠解析 `movie/book/music.douban.com/mine` 页面，写入靠模拟网页端的收藏接口。**豆瓣改版会导致解析失效** —— 设置页有「检查豆瓣读取」自检，能直接看出是登录问题还是选择器失配。
3. **风控**：短时间内大量请求可能触发验证码或 429。默认写入间隔 1.2 秒、翻页间隔 0.8 秒，别调太小。
4. **短评同步默认关闭**：短评是个人表达，写错不可逆。确认流程没问题后再到设置页打开。
5. **豆瓣读写都建议保持一个豆瓣页面打开**：扩展的请求没有浏览器正常浏览时的 Referer，已通过 `declarativeNetRequest` 动态规则补上；若仍被拒，会**自动回退到标签页通道**（把请求注入到你已打开的豆瓣页面里发出去，请求头由浏览器按真实站点生成）。这条路**要求浏览器里至少有一个豆瓣页面开着**，所以同步期间别把它关掉。详见本文「豆瓣写入通道」一节。

## 安装

1. 打开 `chrome://extensions/`
2. 右上角打开「开发者模式」
3. 点「加载已解压的扩展程序」，选择本目录（含 `manifest.json` 的那一层）

需要 Chrome 116 及以上。

### 配置 Bangumi Token

1. **先在新站登录**：打开 <https://next.bgm.tv/demo/login> 完成登录。
   ⚠️ 注意 `next.bgm.tv`（新站）和 `bgm.tv`（旧站）的登录态**不通用**，在旧站登录过不算，必须在新站再登一次。没登录的话下一步的令牌页面是空的。
2. 打开 <https://next.bgm.tv/demo/access-token>（或直接进创建页 <https://next.bgm.tv/demo/access-token/create>），新建令牌：名称随便填，**有效期选最长的那档**（通常 365 天 / 1 年）。
   为什么选最长：**个人令牌不带 refresh_token，扩展没法自动续期**，过期就得重新生成再粘贴一次，选短了是纯粹给自己找麻烦。令牌只存你本地浏览器，不外传；真要止损，去令牌管理页删掉即可（立即失效），这比选短有效期管用得多。
3. **立刻复制令牌字符串** —— 它只在生成时完整显示一次，关掉就找不回来了（只能删掉重建）。
4. 扩展图标 → 设置 → 粘贴到「Access Token」
5. 点「检查授权」，显示用户名即成功

> 域名是 **`next.bgm.tv`**（bgm），不是 `next.bangumi.tv`。写错域名会直接打不开。
> 如果上面链接哪天失效了，就从 <https://bgm.tv> 站内导航找「个人令牌 / 开发者」入口，以站内实际路径为准。
>
> 可选：如果你在 bgm.tv 建过应用（开发者应用页，通常在 <https://bgm.tv/dev/app>），把 client_id / client_secret / refresh_token 也填上，扩展就能在 token 过期时自动续期。不填也能用，只是过期后要重新粘贴。个人令牌有效期约 1 年。

### 配置豆瓣

豆瓣没有公开 API，扩展是模拟网页端请求，所以**必须有真实登录态，并且建议保持一个豆瓣页面开着**：

1. 打开 <https://www.douban.com> 并**登录**。
2. **让这个豆瓣页面保持打开**（放哪个标签页都行，但别把浏览器里所有豆瓣页面都关掉）。
   - 实测经验：浏览器里完全没有豆瓣页面时，读取容易失败；开着豆瓣页面时自检稳定通过。
   - 写入豆瓣的「标签页通道」**必须**依赖一个已打开的豆瓣页面。后台请求被豆瓣拒绝时会自动回退到这条路 —— 把请求注入到你打开的页面里发出去，请求头由浏览器按真实站点规则生成，成功率最高。没有开着的豆瓣页面，这条回退路直接不可用。
3. 回到设置页点「检查豆瓣读取」。看到「通过 · 解析出 N 条」就可以用了。

自检里会有一项 **「豆瓣页面」**，显示当前检测到几个豆瓣页面：

- 显示「通过 · 已打开 N 个豆瓣页面」→ 两条写入通道都可用。
- 显示「注意 · 当前没有打开豆瓣页面」→ 读取可能仍然能用，但写入少了最关键的一条通道。**先去开一个豆瓣页面再继续**。

再点一次 **「读取收藏表单字段」**（同样在「接口自检」里，先填一个豆瓣条目 ID）：它会把豆瓣自己渲染的收藏表单原样列出来 —— 状态字段叫什么、评分字段叫什么、可选值有哪些。认出来了会记住，之后写入时按实测到的字段名发。**建议装机后做一次**，因为字段名叫什么豆瓣没公开，猜错的话请求照样返回 200、状态就是不对，最难查。

#### 实测过的真实表单（条目 1292052，2026-09-27）

这是用户实测读到的一份，直接证明我们早先猜的字段名有两个是错的：

| 豆瓣真实字段 | 类型 | 我们原来的默认名 | 结论 |
| --- | --- | --- | --- |
| `interest` | radio（`wish` / `collect`） | `status` | **猜错了**，已按实测名发 |
| `rating` | hidden | `rating` | 一致 |
| `tags` | text | `tags` | 一致 |
| `private` | checkbox | `privacy` | **猜错了**，已按实测名发 |
| `share-shuo` | checkbox（`douban`） | 运行时探测 | 一致 |

两个修正都按「实测名 + 兼容名一起发」处理（服务端忽略不认识的字段），改名也不会失效。
其中 `private` 还改了语义：它是 checkbox，**只在需要「仅自己可见」时才发 `private=on`**；
以前无条件发 `privacy=0`，万一豆瓣把字符串 `"0"` 当真值，收藏会被悄悄设成仅自己可见且毫无报错。

同一个样本里还有个值得注意的事实：**这份表单的 radio 只有 `wish` / `collect`，没有「在看」**。
这不代表豆瓣不接受「在看」—— 弹窗按条目类型渲染、接口往往另有取值（用户实际同步一条后，
豆瓣上确实是「在看」）。判断依据请以**写入后的回读校验**为准，别看弹窗选项。
- 这一项是「注意」而不是「失败」，因为它不影响读取；但做写入前务必让它变成「通过」。

> 读取失败时按这个顺序排查：① 没登录/登录态过期 → 登录后再试；② 触发风控或验证码 → 在浏览器里手动过一次验证，或调大翻页间隔；③ 豆瓣改版选择器失配 → 把「解析列表页」那步的详情发出来。

## 首次使用（建议按这个顺序）

0. **先在浏览器里登录豆瓣，并留一个豆瓣页面开着**（整个同步过程都别关）。忘了的话自检里「豆瓣页面」这项会提醒你。
1. 设置页 → 把「每个列表最多抓取」设成 `30`，先小批量跑通
2. 设置页 → 点「一键同步」卡片里的 **「准备（扫描并匹配）」**
3. 看结果里「将写入 N 条（→Bangumi X / →豆瓣 Y）」，确认无误 → 点 **「确认写入」**
4. 跑通后再把抓取上限改回 0（不限）

**准备阶段只读不写**，可以随时停在这里；只有点「确认写入」才会真正动两边的数据。
第一次建议先到同步面板跑一遍「演练」。**演练不发起任何写请求**，跑完会自动跳到「演练结果」页签，那份结果就是这次要发的全部请求的完整清单（见下）。

### 收藏状态怎么对应

两侧都是三档，一一对应，不存在强制升级或降级：

| | 豆瓣 | Bangumi | 内部值 |
| --- | --- | --- | --- |
| 想看 | `wish` | 想看（type 1） | `wish` |
| 在看 | `do` | 在看（type 3） | `doing` |
| 看过 | `collect` | 看过（type 2） | `done` |

注意 Bangumi 那边的编号顺序是乱的：**1=想看、2=看过、3=在看**。同步时按标签对应，不按数字大小，所以不会出现「在看被写成看过」。

如果某一条拿不到应该写成的状态，扩展会**拒绝写入并报错**，不会拿「看过」当默认值凑数 —— 早期版本在几处兜底里默认写"看过"（传参缺失、状态认不出、目标侧查不到），「在看」就是这么悄无声息变成「看过」的。现在这些都是显式错误。

#### 「在看」被写成「看过」：怎么查真的原因

先说清楚哪些是**已确认**的、哪些是**曾经猜错**的：

| 结论 | 状态 |
| --- | --- |
| 状态值一直写的是 `do`，没写错 | 已确认（演练结果里能直接看到表单值） |
| 早期版本在几处兜底里默认写「看过」 | 已确认，已全部改成显式报错 |
| ~~「豆瓣只让看过打分，带 rating 会把在看升级成看过」~~ | **猜错了**，已撤回。豆瓣的「在看」本身是可以打分的，这条因果链当时没有任何实测依据，只看到现象就编了原因 |
| 状态字段名可能不是 `status`（豆瓣没公开文档） | 未定 —— 这正是最可能剩下的真凶，下面有实测方法 |

所以现在做了三件事：

| 措施 | 说明 |
| --- | --- |
| **不默认替用户丢评分** | 默认状态与评分照原样一起写。「写『在看 / 想看』时不带评分」降为可选项，默认**关闭** —— 真有人实测到被改写，再自己打开 |
| **写完回读校验** | 每次往豆瓣写完都立刻读回该条的实际状态。对不上时同步面板顶部红字列出「N 条状态校验不符」，写明期望值 vs 豆瓣实际值，并记进日志 |
| **让豆瓣自己说字段名** | 设置页「接口自检」→「读取收藏表单字段」：GET 一次豆瓣自己的收藏弹窗，把里面的表单字段原样列出来（状态字段叫什么、评分字段叫什么、可选值有哪些）。识别到的状态字段名会记住，之后写入时**同时带上实测字段名和兼容字段 `status`** |

> 最后一条是关键。字段名猜错不会报错 —— 请求照样返回 200，状态就是不对，最难查。
> 现在改成读豆瓣自己渲染给自家前端用的表单，并把这个「猜」的环节彻底去掉。
> 每次写入后还有回读校验兜底：到底是我们发错了值，还是豆瓣自己改的，看校验结果就知道。

演练里的静态检查也相应改成如实展示：`状态与评分 → 状态 do（在看）+ 评分 4`，以及
`状态字段名 → 用默认字段名 status（建议实测一次）` 或 `按实测到的字段名发送：interest`。

### 勾选、跳过与批量选择

同步面板每条右侧有三个按钮：`豆瓣 → Bangumi`、`Bangumi → 豆瓣`、`跳过`。

**「跳过」只是取消勾选，不会改动方向。** 各条自己记得之前选了什么，重新勾回来时方向还在原来的那一侧。

早期有个显示 bug：全不选时按钮会错误地高亮成「豆瓣 → Bangumi」。原因是代码算方向时用了 `dirs.every(...)`，而**空数组的 `every()` 恒为 true** —— 数据其实没变，界面在骗人。已修。

**执行同步之后，你剩下的勾选和跳过会保留**，不会全部回到默认全选。已经同步成功的差异自然会消失（两边一致了），没同步的仍保持你之前选的方向或跳过状态。

底部四个批量按钮，语义分两类（这里改过一次，原因值得写下来）：

| 按钮 | 做什么 | 不做什么 |
| --- | --- | --- |
| **全选** | 勾上所有有方向的字段 | 不改任何方向；会**顺带放开方向收窄**（见下） |
| **取消全选** | 取消所有勾选 | **不动方向、不动匹配结果** —— 只是不勾，不是重置；同样放开方向收窄 |
| **只选 豆瓣→Bangumi（N）** | 勾上所有「匹配完本来就建议往 Bangumi 走」的字段，其余取消勾选，**并把列表收窄到该方向** | 不把反向的字段掰过来 |
| **只选 Bangumi→豆瓣（N）** | 同上，方向相反 | 同上 |

括号里的 N 是**按建议方向**算的条数，不是当前勾选数，所以点完一次数字也不会变，能一直看出原本的分布。

**「只选…」会把中间的列表一并收窄到那个方向** —— 批量选完之后不用再一条条翻找哪些被选中了。

- 再点**同一个**按钮 = 放开收窄、回到全部（勾选保持不动，只是显示放开）
- 点**另一个**方向的按钮 = 切过去（旧方向的勾被取消，新方向重新选上）
- 点「全选 / 取消全选」= 一并放开收窄，避免出现「明明全选了、列表还缺一半」
- 切到别的页签也会自动放开（方向筛选只对「差异」页签有意义）

> 收窄只影响显示，**不改变批量按钮的作用范围**：底部的选择作用于当前搜索/分类筛出的全部条目，
> 而不是仅列表里那几条 —— 否则「只选 A 方向」时改点「全选」会漏掉 B 方向。按钮旁会写清「批量只作用于筛出的 N 条；列表仅显示「…」」。

> 旧版的「全部 豆瓣→Bangumi」是**改写**：把每条每个字段的方向全部掰成同一个方向，
> 于是原本该反向同步的字段也被一起翻过去了；「全部跳过」则把方向也清了，看着像整个匹配结果被重置。
> 现在「选择」和「改方向」是两件事：批量只负责选择，方向由你逐条决定或沿用匹配建议。

为了看清哪些字段被改过方向，每条差异的「方向」列会在方向与原建议不一致时标出**（原建议 …）**。

### 演练结果在哪看

点底部「演练」之后**不需要去翻 F12 控制台** —— 跑完会自动切到同步面板顶部的「演练结果」页签，里面每一条都铺开了：

| 内容 | 说明 |
| --- | --- |
| 每条记录一行 | 标题 + 目标侧（豆瓣 / Bangumi），「已就绪」或「构造失败」 |
| Bangumi 请求 | `POST /v0/users/-/collections/{id}` 的完整 JSON body，以及 `5★ → 9 分` 这样的实际换算结果 |
| 豆瓣请求（3 条） | 网页端 `/j/subject/{id}/interest`、移动端 rexxar、移动端 frodo 三条备选通道各自的真实 URL 与表单（`ck` 显示为前 4 位 + 「已取到」）。实际执行按顺序试到第一个成功的为止 |
| 静态检查 | 每条请求下面六个标记：URL 指向豆瓣接口 / URL 含条目 ID / 表单带 ck / 表单有实际内容 / 状态与评分（如实展示，不做因果断言）/ 状态字段名是否实测过（未实测时为黄色提醒） |
| 评分被拦下 | 只有你主动开启「写『在看 / 想看』时不带评分」时才会出现橙色「未写评分」一行，说明为什么这次没写评分 |
| 分享广播 | 「已附上 `share_target=douban` 字段名来源：nearby-分享到」或「未附上 + 原因」 |
| 复制 / 下载 | 右上角「复制全部 JSON」「下载 JSON」，便于贴出来排查 |

演练到此为止**一个请求都没发出去**，所以看到的内容就是真正执行时会发出的那一些。取不到 ck 时会明确标成「构造失败」并说明原因 —— 不会假装成功。

### 分享到豆瓣广播怎么开

#### 先搞清楚它管哪个方向

只有**把 Bangumi 的内容写进豆瓣**时才存在"发豆瓣广播"这回事 —— 对应豆瓣「添加收藏」弹窗底部那个「分享到 ☑ 豆瓣广播」。往 Bangumi 写没有这个环节。

广播**会被你的关注者看到，而且发出去撤不回来**，所以扩展默认一条都不发，要发必须你自己一条条勾。

#### 操作流程（按顺序做）

**第 1 步 · 确认扩展认得这个字段（只做一次）**

设置页 →「接口自检」→ 在「写入测试用的豆瓣条目 ID」里填一个豆瓣条目 ID（比如 `1292052`）→ 点 **「检查分享字段」**。

| 结果 | 怎么办 |
| --- | --- |
| 显示「已识别 分享字段：xxx」 | 好了，记下来了，以后不用再管 |
| 显示「没识别出来」 | 多数是**没登录豆瓣**，或填的 ID 不是电影条目。登录后重试 |

> 为什么有这一步：豆瓣没公开这个接口的文档，字段名只能从它自己的弹窗里读。

**第 2 步 · 在同步面板把方向设成「Bangumi → 豆瓣」**

**这是最容易卡住的一步。** 「分享广播」勾选框**只在该条方向确实是写入豆瓣时才出现**；刚扫完、方向还没定的时候，页面上根本看不到它 —— 不是 bug。

对想发广播的条目，点它那一行的 **「Bangumi → 豆瓣」** 按钮，勾选框会立刻出现在同一行。

**第 3 步 · 勾「分享广播」**

- **逐条**：每条方向按钮左边那个橙色的小「分享广播」勾选框
- **批量**：底部工具栏「分享到豆瓣广播」那一行 →「全部分享」

底部实时显示状态：

- `都不发广播（3 条可发）` —— 已符合"会写入豆瓣"的有 3 条，但都还没勾
- `已选 2 条会发广播（广播发了撤不回，注意）`
- `需先把方向设为「Bangumi → 豆瓣」才有「分享广播」可选` —— 就是卡在第 2 步了

**第 4 步 · 先演练确认**

点底部 **「演练」**，跑完自动跳到「演练结果」页签。每条豆瓣请求下面都有一行「分享广播」：

- `已附上 share_target=douban 字段名来源：nearby-分享到` → 正常，真执行时会带上
- `未附上` + 原因 → 这次只会写收藏、不发广播

**第 5 步 · 确认无误再执行**

点 **「执行同步」**。确认框会单独提示一句「其中 N 条会同时发到豆瓣广播 —— 广播会被关注者看到，且发出后撤不回来」，这是最后一次反悔的机会。

#### 卡住了看这里

| 现象 | 原因 |
| --- | --- |
| 找不到「分享广播」勾选框 | 这条的方向还是「豆瓣 → Bangumi」或「跳过」。先点「Bangumi → 豆瓣」 |
| 「全部分享」点了没反应 | 没有任何一条是写入豆瓣的方向。同上 |
| 勾了但广播没出现 | 看演练结果里「分享广播」那一行。显示「未附上」就是没读到字段名，此时收藏照样写成功、只是没发广播 |
| 完全没有这个按钮 | 用的是设置页/弹窗的「一键同步」，那条路径没有逐条界面，固定**不分享**广播。要分享就走同步面板 |

### 一键同步的三个入口

| 入口 | 位置 | 适合 |
| --- | --- | --- |
| 设置页「一键同步」卡片 | 扩展选项页 | 主要入口，能看完整预览 |
| 弹窗「一键同步」 | 点扩展图标 | 快速跑一次 |
| 同步面板 | 点扩展图标 → 同步面板 | 要逐条指定方向时用 |

三个入口共用同一套流程：**扫描 → 双向匹配 → 算差异 → 确认 → 写入**。
结果在后台缓存 10 分钟，「准备」之后直接「确认写入」不会重复扫描。

### 「待确认匹配」条目怎么建立对应

这一栏是 **豆瓣有收藏、但没能在 Bangumi 上定下对应条目**的记录。处理方式与「Bangumi 独有」完全对称：

**首选「批量反查 Bangumi」**：拿豆瓣标题逐个去 Bangumi 搜，置信度达标的自动建立对应，
其余把候选列在条目下方，点「用它」即可。（Bangumi 搜索有限流，量大时会比较慢。）

逐条补的办法：

| 操作 | 说明 |
| --- | --- |
| **搜 Bangumi** | 单条搜索并把候选列出来点选，不擅自替你决定 |
| **去 Bangumi 搜**（推荐） | 直接打开 Bangumi 搜索页，自己找到条目后把地址里的**数字 ID** 粘回输入框，点「确定」。自动搜索失效时这条路永远可用 |
| 手动填 ID | 已知 Bangumi subject ID 时直接填数字，点「确定」 |
| 跳过此条 | 写进映射表标记为跳过，以后不再重复匹配 |

> **为什么以前搜不准**：豆瓣标题常写成「中文名 / 原名」一整串，
> 拿整串去 Bangumi 搜索会把原名也塞进关键词，召回明显变差；
> 打分时两边标题也都要拆成「主标题 / 原名」再交叉比对，
> 否则同一部作品会被另一半语言稀释成低分。现在两边都拆开处理。
> 另外**年份差 3 年以上**即使标题完全一样也不自动采纳，会压到候选区让你确认 —— 那是同名不同作品。

搜不到时先看**搜的是什么关键词**：优先用中文标题；纯外文原名在 Bangumi 上可能搜不到，这时改用中文译名或去 Bangumi 页面自己找。

### 「Bangumi 独有」条目怎么建立对应

这一栏是 **Bangumi 有收藏、但豆瓣列表里找不到对应条目**的记录。要在豆瓣侧为它们新建收藏，必须先告诉扩展「这条 Bangumi 条目对应豆瓣的哪个条目 ID」。

**首选「批量反查豆瓣」**：拿这批条目的标题逐个去豆瓣搜，置信度达到阈值的直接自动建立对应，
剩下的把候选列在条目下方，点「用它」即可 —— 不用再一条条点「搜豆瓣」。
（豆瓣搜索有频率限制，间隔取「翻页间隔」但不低于 1 秒，量大时会比较慢。）

批量跑完仍有遗漏时，再用下面的办法逐条补：

| 操作 | 说明 |
| --- | --- |
| **搜豆瓣** | 按单条标题去豆瓣搜索并列出候选，选中即用。会依次尝试 `search.douban.com`、`{site}.douban.com`、全站搜索三个入口 |
| **去豆瓣搜**（推荐） | 直接打开豆瓣搜索页，你在页面上自己找到条目，把地址里的**数字 ID**（形如 `subject/1292052`）粘回输入框，点「建立对应」。**自动搜索解析失效时这条路永远可用** |
| 手动填 ID | 已知 ID 时直接填数字，点「建立对应」 |

> **匹配打分说明**：豆瓣搜索结果的标题常是「中文名 / 原名（年份）」的形式。
> 扩展会把两边的标题都拆成「主标题」和「原名」再交叉比对，
> 否则原名会把相似度稀释掉 —— 例如「进击的巨人 最终季 / 進撃の巨人 The Final Season」
> 整串直接比只有 0.57（低于阈值、判为不匹配），拆开比对则是 1.00。

搜不到时的排查：**先看搜的是什么关键词**（搜索时会显示出来）—— Bangumi 条目优先用中文名 `name_cn`，如果没有中文名就用原名，纯日文原名在豆瓣上很可能搜不到。这种情况用「去豆瓣搜」，改成中文译名或原名再搜一次。

搜索结果会标注来源：**内嵌数据**表示从页面内嵌 JSON 里取的，**页面结构**表示从 DOM 里解析的。两者都取不到时会列出每个入口的 HTTP 状态和字节数，便于判断是被风控拦截还是页面改版。

## 界面说明

### 筛选：搜索栏 + 分类 + 方向

页签上方有几个可以叠加使用的筛选，都**只决定当前页签显示哪些条目**：

**搜索框** —— 输入即筛选。匹配范围包括**豆瓣标题、豆瓣原名、Bangumi 标题、条目 ID**，大小写不敏感。

**分类按钮** —— `全部 / 想看（N）/ 在看（N）/ 看过（N）`，点一下只看那一类收藏，再点一次取消。按钮上的数字是**当前页签里该分类有多少条**，始终按「这个页签各类收藏的分布」算，**不会因为你正在看某一类而变化**；只跟搜索词联动。

**方向筛选** —— 点底部的「只选 豆瓣→Bangumi / Bangumi→豆瓣」时，列表会一并收窄到那个方向（「只选…」本身的选择语义见上一节）。它按**匹配完的建议方向**判定，与按钮上的口径同源。

- 分类按**任一侧**的收藏状态判定。豆瓣「看过」+ Bangumi「在看」这种本身就有差异的条目，选「在看」和选「看过」都会出现 —— 它两边都占，硬选一边会让它从视野里消失。因此**三个数字之和可能大于「全部」**，这不是算错
- **只影响显示，不改任何勾选**：筛掉的条目仍然保持你之前设的方向与勾选，取消筛选就都回来了
- **批量操作跟着筛选走**：底部「全选 / 取消全选」「全部分享 / 全部不分享」只作用于搜索/分类筛出来的那几条；「只选某方向」除了做选择，还会把列表收窄（收窄不改变批量作用范围，见上一节）
- 顶部显示「筛出 X / Y 条（搜索词「…」+ 分类「在看」+ 方向「…」）」，页签上的计数仍是全量；筛选后列表为空时会说明是被哪几个条件筛掉的
- 「清除」按钮会一并解除搜索词和分类（方向筛选用「再点一次同一个按钮」或切页签来放开）
- 方向筛选**只对「差异」页签有意义**，切到其它页签会自动放开

> 「Bangumi 独有」和「待确认匹配」里的批量反查按钮同样只反查当前筛出来的条目 —— 想先试几条再放开全量时很好用。

### 各页签

- **差异**：每条显示豆瓣侧和 Bangumi 侧的字段值对比，你可以逐字段勾选，也可以整条切换方向（豆瓣→Bangumi / Bangumi→豆瓣 / 跳过）。底部四个批量按钮只做「选择」：全选、取消全选、按建议方向只选某一边（详见上文）
- **待确认匹配**：豆瓣有收藏、Bangumi 侧还没定下对应条目的记录，可以「批量反查 Bangumi」或逐条「搜 Bangumi」，确认后写入映射表，以后不再重复匹配
- **Bangumi 独有**：Bangumi 有收藏、豆瓣列表里找不到的条目。指定它的豆瓣条目 ID（可以点「搜豆瓣」自动找）后，就能把这条收藏推到豆瓣
- **日志**：抓取和写入的流水，排查问题用

## 豆瓣写入通道（重点）

豆瓣的收藏接口对请求来源有校验，扩展直接 fetch 容易吃闭门羹。这里做了两条通道：

| 通道 | 原理 | 代价 |
| --- | --- | --- |
| 后台请求 | service worker 直接 fetch，用 dNR 动态规则补 Referer/Origin | 不需要额外操作，但可能仍被豆瓣拒绝 |
| 标签页注入 | 把请求注入到你打开的豆瓣页面，在页面上下文执行 | 需要开着一个豆瓣页面，但请求头最真实，成功率最高 |

默认是 `auto`：先试后台，全失败就自动切标签页，成功后把通道偏好记下来。

**另一个实现细节**：请求头规则用的是**动态规则**而不是 manifest 里的静态规则集。原因是静态规则无法把作用范围限定到"扩展自己发出的请求"，会连带改写你在豆瓣网页上正常操作的 XHR 的 Referer，把网站自身的按钮弄坏。现在只匹配 `movie.douban.com/j/`、`/mine`、`/subject/` 等具体路径，影响面压到最小。

规则丢了怎么办：设置页 →「检查请求头规则」，显示 0 条的话重新加载一次扩展即可。

## 项目结构

```
manifest.json                  MV3 清单
src/
  background/
    service-worker.js          消息路由、扫描编排、同步执行
    header-rules.js            dNR 动态请求头规则
  core/
    normalize.js               统一数据模型（状态/分类/评分归一）
    rating.js                  1-5 星 ↔ 1-10 分 换算
    matcher.js                 正向匹配：豆瓣条目 → 搜 Bangumi
    reverse-matcher.js         反向匹配：Bangumi 孤儿条目 → 搜豆瓣
    diff.js                    双向差异计算
    sync.js                    写入执行
  adapters/
    bangumi.js                 Bangumi 官方 API
    douban.js                  豆瓣读取与写入
    douban-parse.js            豆瓣页面解析（纯函数，可单独调试）
  offscreen/parse.js           service worker 没有 DOMParser，借这里解析 HTML
  ui/
    lib/dialog.js              页面内确认框/提示条（不用原生 confirm）
    lib/msg.js                 与 service worker 通信
    popup / options / sync     三个界面
tests/                         回归测试
tools/pack.py                  打包成可分享的安装包（含分发前自检）
```

### 打包给别人安装

```bash
python tools/pack.py                      # 输出到 F:/douban-bangumi-sync-v<版本号>.zip
python tools/pack.py --src . --out dist   # 也可以指定源目录和输出目录
```

它只收扩展真正需要的东西（`manifest.json` / `src/` / `icons/` / `README.md`），附一份中文安装说明，
并且**打包前先自检**：manifest 引用到的每个文件、HTML 里每个本地 `src`/`href`、JS 里每个相对 `import`
都必须真的存在于包里，有一处缺失就报错退出、不产出 zip ——
分发出去才发现漏文件，对方看到的是白屏或报错，最难查。

包里不含任何个人信息：豆瓣登录态读的是浏览器 cookie，Bangumi 令牌存在浏览器自己的扩展存储里，
两者都不进 zip。（源码里的 `apiKey` 是豆瓣网页公开的那个前端 key，不是密钥。）

对方收到后按包内「安装说明.txt」走：解压到固定目录 → `chrome://extensions` 开开发者模式 →
「加载已解压的扩展程序」。**Chrome 73 之后双击 crx 直接安装这条路已经封了**，
非商店扩展只有开发者模式加载一种方式，这一点最好提前跟对方说清楚。

```bash
npm i -D jsdom          # 只有解析测试需要
npm test
```

- `tests/core.test.mjs` — 评分换算（含自定义表与脏数据）、标题匹配、差异对比、映射缓存（83 项）
- `tests/reverse.test.mjs` — 反向匹配：标题拆分、候选打分、阈值判定、站点路由（37 项）
- `tests/parse.test.mjs` — 豆瓣列表页解析、状态映射、兜底选择器、**分享到广播字段解析**（51 项）
- `tests/search.test.mjs` — 豆瓣搜索页解析（内嵌 JSON / DOM 兜底 / 边界）（28 项）
- `tests/nav.test.mjs` — 扩展内页面跳转：原地跳转 / 同源判定 / 降级新开，以及「UI 里不许裸用 chrome.tabs.create」的守卫（20 项）
- `tests/douban-write.test.mjs` — 豆瓣写入通道：**演练必须一次写请求都不发**（含标签页注入这条真实写通道）、分享字段注入、读不到字段时的降级、**演练要产出真实可用的请求明细而不是空壳**、取不到 ck 时演练须判失败、**默认不许替用户丢评分**（默认值守卫）、写完回读校验（58 项）
- `tests/douban-form-probe.test.mjs` — 收藏表单字段探测：从豆瓣真实弹窗里读出状态/评分/隐私字段名（radio 与 select 两种形态都认）、认不出就说认不出、**读到的字段名必须真被写进请求**、**隐私字段只在需要时出现**（不许发 `privacy=0`）、读不到时不装成功。含一份用户实测的真实表单样本（42 项）
- `tests/status-mapping.test.mjs` — 收藏状态三方往返一致、**未知状态不许默认成「看过」**（含「连请求都不该发出去」的断言）、面板方向判定里空数组 `every()` 的回归、**批量选择语义**（建议方向不受手动改动影响 / 只选某方向只取消勾选不改写其余 / 全选取消全选不碰方向）（62 项）
- `tests/forward-match.test.mjs` — 豆瓣 → Bangumi 的正向匹配：关键词要拆掉原名、候选打分要主标题/原名交叉比对、年份差太远不许自动采纳（11 项）
- `tests/options-rating.test.mjs` — 用 jsdom 加载真实设置页，验证自定义换算表的渲染/诊断/保存（24 项）
- `tests/ui-dialog.test.mjs` — 页面内确认框行为，以及「UI 里不许再出现原生 confirm/alert」的守卫（24 项）
- `tests/sync-panel.test.mjs` — 用 jsdom 加载真实同步面板：**搜索栏只改显示、不动勾选**，**分类筛选（想看/在看/看过）按任一侧状态判定且同样不动勾选**，**方向筛选（只选某方向时列表一并收窄，切方向 / 全选 / 切页签都会放开）**，批量按钮与批量反查的作用范围跟着筛选走，**取消全选后还能全选回来（方向没被抹掉）**，**分类按钮上的计数不随当前分类变化**（曾经因此把「全部」显示成在看总数），新按钮必须真的挂上（68 项）
- `tests/dom-ids.test.mjs` — 页面 JS 引用的元素 id 必须在 HTML 里真实存在（含 JS 动态注入的那批），顺带校验 div 开闭配平（6 项）

合计 **514 项**。

> 其中有几个是**守卫型**测试：`nav` 里禁止在 UI 层裸用 `chrome.tabs.create`（否则设置页每进一次同步面板就多开一个标签页），
> `ui-dialog` 里禁止原生 `confirm/alert`（内嵌宿主会拦掉，表现为"点了没反应"），
> `douban-write` 里禁止演练走到标签页注入（那会真的写入）。改坏了会直接测试失败，不是靠记性。

豆瓣改版后如果解析挂了，先跑 `npm run test:parse`，把假数据里的 HTML 换成你实际抓到的页面结构，就能快速定位是哪一步失配。
